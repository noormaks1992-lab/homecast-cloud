# تحديث دشوف من GitHub عند إعادة التشغيل

## السلوك

يراقب المشغّل عند كل بدء فرع `noor-player-m3u` في المستودع الخاص
`noormaks1992-lab/homecast-cloud`، ويقرأ إصدار المشروع من
`dshoof-player/source.snapshot.json`. هذا هو الملف الذي نحفظ فيه حاليًا شفرة
المشروع كاملة. تعديل ملفات أخرى خارج هذا الإصدار لا يغيّر التطبيق المنشور.

بعد إعداد الربط مرة واحدة، يكفي تحديث إصدار المشروع في GitHub ثم الضغط على
Restart في Botkeep. لا تحتاج رفع الملفات مجددًا. التحديث لا يحدث أثناء البث
من دون إعادة تشغيل؛ إعادة التشغيل نفسها تقطع الاتصال مؤقتًا.

## إعداد واحد فقط على Botkeep

1. ضع `github-start.mjs` بجانب `server.mjs` و`supervisor.mjs` في جذر التطبيق.
   الملف المستقل منشور أيضًا في المستودع لتسهيل التنزيل من حساب GitHub.
2. في GitHub أنشئ Fine-grained personal access token يقتصر على هذا المستودع،
   وبصلاحية Contents: Read-only. اختر مدة صلاحية تناسبك؛ انتهاء المفتاح يمنع
   جلب التحديثات لكنه لا يمنع تشغيل النسخة الموجودة.
3. احفظه في متغير بيئة الاستضافة `DSHOOF_GITHUB_TOKEN`، أو في ملف `.env`
   الموجود على الاستضافة. لا ترفعه إلى GitHub ولا تضعه في واجهة المشاهدين.
4. اجعل أمر البدء:

   ```sh
   node --env-file-if-exists=.env github-start.mjs
   ```

5. احتفظ بـ Node 22 أو أحدث، وبالمنفذ الحالي `SERVER_PORT=33085` وإعداداتك
   الموجودة. لا تحذف `data/` أو `.env`. اضغط Restart مرة واحدة.

الطريقة لا تحتاج كتابة كلمة مرور حساب GitHub في الكود ولا إلى webhook عام.
النشر غير مفعّل على Botkeep من هذه المحادثة بسبب تعطل أداة المتصفح؛ كتابة
الملفات على GitHub وحدها لا تكفي لتثبيت هذا المشغّل أول مرة.

## حماية الاستمرارية والبيانات

- تنزيل محدود الحجم والمهلة من API GitHub عبر HTTPS مع منع إعادة توجيه الطلب
  الذي يحمل المفتاح.
- النسخة الجديدة تُجهّز في مجلد منفصل؛ يتم فحص صياغة ملفات JavaScript وتوفير
  اعتمادياتها قبل التشغيل. تعذّر التنزيل أو الفحص أو التثبيت يبقي النسخة السابقة.
- مجلد البيانات ثابت بمسار مطلق عبر DATA_DIR؛ الروابط والمفاتيح والإعدادات
  والدعوات تظل في مكانها. لا تُنسخ من GitHub ولا يُسمح للإصدار بالكتابة فوقها.
- يحتفظ بملف المشغل المحلي `public/hls.min.js` إن لم يكن ضمن الإصدار.
- لا يمرّر مفتاح GitHub إلى التطبيق أو FFmpeg أو أوامر تثبيت الحزم.
- يقبل النسخة بعد نجاح فحص `/healthz` خلال 45 ثانية. عند فشل بدء التشغيل
  يعود إلى الإصدار السابق. هذا يتحقق من بدء التطبيق، وليس نجاح المصدر الخارجي.
- يحتفظ بآخر إصدار فعّال وسابقه، وينظف الإصدارات واعتمادياتها غير المستخدمة.
- النسخة الأصلية في جذر الاستضافة تبقى مرجع الرجوع الأول. لتجاوز التحديث
  وتشغيل تلك النسخة يدويًا يمكن إعادة أمر البدء القديم:
  `node --env-file-if-exists=.env supervisor.mjs`.
- مشغّل البداية المثبت في الجذر ثابت؛ الإصدارات تحدث التطبيق الذي يشغله.
  تعديل مشغّل البداية نفسه مستقبلًا يحتاج استبداله مرة واحدة.

## التحقق

ابحث في Console عن `[github-update] active release` واسم الإصدار.
يعرض `/healthz` حقل `release` للنسخة النشطة عند تشغيلها عبر الربط.
عند فشل بدء التحديث يظهر `new release failed startup; reverting`.

الاختبارات تحققت من جلب إصدار جديد، الرجوع عند تعطل GitHub أو خطأ في الشفرة،
الرجوع بعد تعطل بدء النسخة الجديدة، الحفاظ على البيانات، وعدم تمرير المفتاح
إلى التطبيق. لا توجد ضمانة لعدم انقطاع مزوّد البث أو الاستضافة أو لترحيل
بيانات غير متوافق في إصدار مستقبلي.

مرجع صلاحية القراءة وواجهة GitHub الرسمية:
https://docs.github.com/en/rest/repos/contents#get-repository-content

نتيجة التحقق المحلي لهذا الإصدار: `node --test` — 43 اختبارًا ناجحًا، دون فشل أو تخطٍّ.
